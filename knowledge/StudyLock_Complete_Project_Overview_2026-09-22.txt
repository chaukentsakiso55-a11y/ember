================================================================================
1. WHAT STUDYLOCK IS
================================================================================

StudyLock is a connected education and focus-control ecosystem designed to help a student study without distractions while giving approved parents and teachers controlled ways to support the student.

The project grew from a single student focus app into a multi-app system made of:

1. StudyLock Student
2. StudyLock Parent
3. StudyLock Teacher
4. StudyLock Parent HTML Dashboard
5. Earlier desktop/Windows StudyLock experiments
6. Shared Firebase / connected-system infrastructure
7. Offline learning libraries and imported knowledge packs

The main goals of StudyLock are:

- Keep the student focused during study sessions.
- Block selected distracting apps.
- Prevent a student from casually disabling protection during an active session.
- Provide an AI Tutor.
- Work as much as possible without internet.
- Allow the Parent app to pair with the Student app.
- Allow the Parent app to remotely start or manage study controls.
- Allow the Teacher app to share school content with students.
- Track study time, focus state, AI usage, blocked apps, schedules, goals, and other learning information.
- Provide quizzes, notes, planning, progress tracking, rewards, learning resources, and study tools.
- Use a recognizable StudyLock liquid/glass-style interface.
- Keep Student, Parent, and Teacher as separate applications while allowing them to communicate.

11. PAIRING SYSTEM
================================================================================

StudyLock pairing has used several approaches over its development.

PAIRING METHODS
---------------

- 6-digit pairing codes.
- QR codes.
- Deep-link style pairing concepts such as:
  studylock://pair
- Firebase/Firestore pairing channels.
- LAN/same-Wi-Fi experiments.
- Parent HTML communication approaches.

PARENT CODE GENERATION
----------------------

A repeated issue was that the Parent "Generate new key" or pairing-code button did not work correctly in some APK builds.

Repairs attempted to make the Parent app:

- Generate codes locally and immediately.
- Display codes without waiting for Firebase.
- Generate a QR from the code.
- Publish the pairing channel to Firebase.
- Show connection state.
- Fall back to Firebase REST communication in some repaired builds.

SAME-WIFI / LAN
---------------

Same-Wi-Fi communication was explored as an option.

Some native v5 designs included LAN pairing/sync concepts.

However, Firebase and LAN are different systems:
- Firebase can synchronize across different networks if internet and backend configuration work.
- LAN can work between devices on the same local network if the apps implement direct local networking correctly.

Having both phones on the same Wi-Fi does not automatically make two StudyLock APKs connect unless the APKs actually contain the same LAN protocol, ports, discovery method, permissions, and message format.

12. WHY THE PARENT HTML COULD CONNECT WHEN THE PARENT APK COULD NOT
================================================================================

This became one of the key StudyLock debugging questions.

The Parent HTML and Parent APK sometimes looked like they were supposed to perform the same job, but they did not necessarily use the same backend or protocol.

At least one recorded HTML Parent dashboard used:
- ntfy.sh
- localStorage

while Android versions were designed around:
- Firebase
- Firestore
- Firebase Authentication
- REST fallback in some repairs

Therefore, the HTML successfully connecting did not prove the Parent APK's Firebase communication was configured correctly.

Potential causes investigated across different builds included:

- Parent and Student using different Firebase projects.
- Different collection names.
- Different pairing-code formats.
- Firestore rules blocking the Parent app.
- Anonymous Authentication not enabled.
- Parent app not publishing its pairing channel.
- Student app expecting a different document structure.
- Missing google-services configuration.
- Incorrect package name in Firebase.
- Stale or incorrect Firebase project configuration.
- REST requests using the wrong project/collection.
- UI generating a code but not writing it remotely.
- Parent app expecting the Student to respond through a different transport.
- Student waiting for a dashboard heartbeat that the Parent APK never sends.
- HTML using an entirely different transport than the Android app.

A later goal was to copy the actual working connection logic from the Parent HTML where possible while retaining the Parent app's native structure and design.

- app/build.gradle.kts in one commit.
- parent/google-services.json in one commit.

Any exposed private/API credentials should be rotated or restricted rather than treated as secret merely because they are embedded in an APK or repository.

15. APP BLOCKING
================================================================================

StudyLock uses Android Accessibility capabilities to detect foreground apps and redirect/block selected distractions.

Known examples of default-blocked apps in one build:
- Chrome
- YouTube

Later versions added:
- Installed-app picker.
- Blocklist persistence.
- Weekly blocklist performance work.
- Parent visibility of blocked apps.

The Accessibility Service is important because Android does not normally allow a regular app to simply close any other app at will.

The blocking flow can:
- Detect an unwanted foreground package.
- Redirect the user.
- Show the StudyLock focus interface.
- Maintain block state during a focus session.

LIMITATIONS
-----------

- Accessibility permission must be granted by the user.
- Some manufacturers aggressively stop background services.
- Browser website blocking is harder than package/app blocking.
- Android security updates can change behavior.
- A regular Device Admin app cannot completely prevent the device owner from eventually removing it.

16. DEVICE ADMIN, PIN, AND UNINSTALL PROTECTION
================================================================================

One of the most important StudyLock security requirements is that the student should not be able to disable protection without authorization.

PIN
---

A 6-digit PIN has been used for:
- First launch.
- Settings protection.
- Admin deactivation approval.
- Uninstall-release concept.
- Parent/security controls.

The desired behavior:

1. First launch asks for or creates the 6-digit PIN.
2. StudyLock is granted the required admin/accessibility permissions.
3. The user cannot simply enter settings and disable the protection without the PIN.
4. Uninstall should require an authorized release process.

REPORTED PROBLEM
----------------

The user repeatedly reported that StudyLock could still be uninstalled because Android allowed Device Admin to be deactivated without StudyLock successfully forcing a PIN first.

This is a platform-level issue as well as an implementation issue.

Classic Device Admin does not give a normal third-party Android application absolute control over Settings or the package installer.

TRUE STRONGER LOCKDOWN
----------------------

For significantly stronger uninstall prevention, Android Device Owner / managed-device deployment is generally required.

Some StudyLock native v5 work referred to:
- Device Owner
- Lock Task

But a consumer-installed APK cannot silently make itself Device Owner on an already configured phone.

Therefore, "PIN before uninstall" can be approximated in a normal app, but cannot be guaranteed against the actual device owner unless the device is enrolled/managed in a supported Android management mode.

40. STUDYLOCK SECURITY MODEL
================================================================================

StudyLock combines several layers:

LAYER 1 — APPLICATION PIN
- Prevent casual access to protected settings.

LAYER 2 — ACCESSIBILITY SERVICE
- Detect and block distracting apps.

LAYER 3 — DEVICE ADMIN
- Provide additional administrative protection.

LAYER 4 — FOCUS SESSION RULES
- No pause / controlled ending.

- Parent can control or approve certain changes.

- Stronger managed-device option where Android enrollment supports it.

No single normal Android permission makes an app impossible for the actual device owner to remove.

================================================================================

The finished StudyLock system should follow these principles:

1. STUDY FIRST
The core purpose is to improve focus and learning, not just monitor the student.

2. OFFLINE CAPABLE

Parent and Teacher controls should synchronize reliably when connectivity is available.

Do not turn StudyLock into secret message surveillance.

Use PIN, Accessibility, Device Admin, and managed-device features correctly without falsely claiming a normal APK can become impossible to uninstall.

7. ONE DESIGN FAMILY
Student, Parent, and Teacher should clearly look like StudyLock.

Every release APK must be:
- parseable
- signed
- installable
- correctly versioned
- tested

9. REAL TESTING
A successful Gradle build is not enough.
Pairing, blocking, security, offline behavior, and syncing must be tested on physical Android devices.

10. SEPARATE APPS, SHARED SYSTEM
Student, Parent, and Teacher remain separate APKs but share a common protocol and backend schema.

51. SIMPLE DESCRIPTION OF STUDYLOCK
================================================================================

StudyLock is a Cyber Pulse learning and focus ecosystem made of Student, Parent, and Teacher apps.

The Student app helps a learner focus, blocks distracting apps, runs protected study sessions, provides quizzes, notes, planning, progress tools, learning libraries, and an AI Tutor that can use both online and offline information.

The Parent app pairs with the Student app using a code or QR and is designed to view study information, manage schedules, control Auto Study, start or authorize focus sessions, and manage protection-related settings.

The Teacher app connects to students for academic purposes such as sending notes, assignments, questions, resources, announcements, and visual/class content.

The system has evolved through many Android, HTML, Firebase, offline-library, and security builds. Its biggest technical challenges have been reliable Parent/Student/Teacher synchronization, Firebase configuration, APK signing/install compatibility, offline learning databases, and Android's limitations around uninstall prevention.

The current direction is to keep all three apps separate, make them share one reliable communication protocol, preserve the Student app's features, redesign Parent and Teacher to match the Student's liquid yellow/orange visual language, and verify every feature on real devices.
